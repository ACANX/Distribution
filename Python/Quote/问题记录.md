# 问题记录

## 001 — Open 计算精度丢失

### 问题描述

对 Latest.mvsv 做 8→11 列扩展时，第一条记录的开盘价（Open）通过 `Open = Close - ChangePrice` 计算。直接使用 Python `float` 运算后 `str()` 转换导致精度丢失。

**示例（518880）**：

```
Close = "9.001", ChangePrice = "-0.251"
期望: Open = "9.252"
实际:  Open = "9.251999999999999"
```

### 原因

Python `float` 是 IEEE 754 双精度浮点数（64-bit），`9.001 - (-0.251)` 在二进制中无法精确表示，浮点运算结果为 `9.251999999999999...`。直接用 `str()` 转换暴露了内部表示精度。

### 排查过程

1. 首次修复尝试：使用 `round(value, 6)` 统一保留 6 位小数
   - 问题：Open 的精度与输入不一致。例如 `Close=135, CP=0` → `Open="135.000000"` 不应有多余的 0

2. 最终方案：**从输入字符串提取精度位数，按 max(prec_close, prec_cp) 格式化输出**
   - 读取 Close 和 ChangePrice 的字符串原始值
   - 统计小数点后的位数
   - 取两者最大位数作为输出精度
   - 用 `format(value, f".{prec}f")` 格式化

### 解决方案

`mvsv.py` 中 `_expand_to_11cols` 函数新增 `_calc_open` 辅助函数，使用 `decimal.Decimal` 确保精确计算：

```python
def _calc_open(close_str, cp_str):
    from decimal import Decimal
    close_d = Decimal(close_str)
    cp_d = Decimal(cp_str)
    result = close_d - cp_d
    prec = max(
        -close_d.as_tuple().exponent if close_d.as_tuple().exponent < 0 else 0,
        -cp_d.as_tuple().exponent if cp_d.as_tuple().exponent < 0 else 0,
    )
    if prec:
        result = result.quantize(Decimal('0.' + '0' * prec))
    return str(result)
```

**关键点**：
- 使用 `Decimal` 而非 `float`，消除二进制浮点精度误差
- 通过 `as_tuple().exponent` 获取输入精度（小数点后位数）
- 用 `quantize()` 按最大精度格式化输出
- `Decimal` 是 Python 标准库模块，无需额外依赖

### 验证结果

| 证券 | Close | ChangePrice | precision | Open |
|---|---|---|---|---|
| 518880 | 9.001 | -0.251 | 3 | **9.252** ✅ |
| GCMain | 4352.2 | -1.7 | 1 | **4353.9** ✅ |
| NVDA | 210.155 | 5.055 | 3 | **205.100** ✅ |
| SPCX | 135 | 0 | 0 | **135** ✅ |
| USDCNY | 6.7655 | 0 | 4 | **6.7655** ✅ |

## 如何规避此类问题

浮点数精度问题是工程中的常见陷阱，以下规范可有效规避：

### 1. 凡是金额/价格计算，使用 Decimal 而非 float

```python
from decimal import Decimal

# ❌ 错误
open_val = str(float(close) + float(cp))

# ✅ 正确
close_d = Decimal(close_str)
cp_d = Decimal(cp_str)
result = close_d - cp_d
# quantize 到输入精度
prec = max(-close_d.as_tuple().exponent, -cp_d.as_tuple().exponent)
result = result.quantize(Decimal('0.' + '0' * prec))
return str(result)
```

### 2. 字符串到字符串的数值转换，始终使用 Decimal

mvsv 中所有数值字段以字符串形式存储，任何数值计算（加减乘除、汇总）都必须：
1. 读取输入字符串
2. 构造 `Decimal` 对象
3. 计算
4. 用 `quantize()` 确定输出精度
5. `str()` 输出

### 3. 在代码审查中检查精度路径

涉及以下操作时必须检查精度处理逻辑：
- 从现有字段计算新字段（如 Open 从 Close + ChangePrice 推导）
- 多行聚合（如求和、平均）
- 字段类型转换（如 str → Decimal → str）

### 4. 测试边界值

添加包含以下特征的用例：
- 整数结果（Close=135, CP=0 → Open="135"）
- 不同精度输入（Close=6.7655, CP=0 → Open="6.7655"）
- 纯整数输入（Close=100, CP=10 → Open="110"）
- 高精度输入（Close=0.0001, CP=0.00005 → Open="0.00005"）

## 002 — 月归档因缺失交易日被错误跳过

### 问题描述

`Task03ArchiveMonthly.py` 在月内缺少部分日归档文件时，将整个月判定为不完备并直接跳过月聚合。这样会阻断月归档的增量更新：已有日数据无法进入月文件，后续补齐数据前也没有可继续合并的月归档结果。

### 原因

`check_completeness()` 原先返回布尔值；只要发现缺失交易日，`process_code()` 就记录 WARNING 并立即返回，没有执行日文件合并和月文件写回。

### 解决方案

`Task03ArchiveMonthly.py` 现在将完备性检查改为返回缺失交易日列表：

- 缺失交易日仅记录为 INFO，并继续聚合现有日归档文件
- 月归档元数据的 `# 备注` 和 `# Remark` 写入 `月归档缺失交易日: ...`
- 保留已有备注内容，并在每次增量运行时重新计算缺失日期
- 后续补齐日归档后，已恢复日期会从缺失说明中移除，避免备注过期

### 验证结果

- 月内仅有部分日文件时，月归档仍能生成并包含已有数据
- 增量补入日文件后，月归档行数增加，缺失日期备注同步刷新
- 缺失交易日场景不再输出 WARNING

## 003 — 日归档与 Latest 清理窗口混用

### 问题描述

按日归档和 `Latest.mvsv` 清理是两个不同的生命周期操作：数据达到约 10 天时应先复制归档到按日目录，但在此时仍需保留在 `Latest.mvsv` 中；只有达到约 21 天、超出 Latest 保留窗口后，才应从 `Latest.mvsv` 清理。旧逻辑在 10 天归档时同时删除了同一批 Latest 数据，导致 Latest 的保留窗口失效。

### Git 历史

该调整记录在提交 `c3613fa9b0`（2026-07-05）：

- 原逻辑使用同一批 `archive_candidates` 完成日归档，并立即按 `ts` 从 `latest.rows` 移除
- 修复后删除归档阶段的移除逻辑，日归档变为复制导出
- 归档线使用 `DailyArchiveAfterDays=10`
- 清理线单独使用 `LatestWindowDays=20`
- 两条 cutoff 均按北京时间自然日 00:00 对齐，因此数据进入第 21 个自然日后才从 Latest 清理

### 解决方案

`Task02ArchiveDaily.py` 分离两个阶段：

1. 将超过 10 个自然日的数据写入 `Archive/Finv/SecuQuote/Day/{code}/`，不修改 `Latest.mvsv`
2. 仅将超过 20 个自然日的数据从 `Latest.mvsv` 裁剪并单独提交
3. 归档提交和裁剪提交完成后统一 push；没有任何变更时跳过提交

### 相关文件

- `Python/Quote/Task02ArchiveDaily.py` — 日归档与 Latest 裁剪窗口
- `Python/Quote/Config.yaml` — `DailyArchiveAfterDays` 和 `LatestWindowDays`
- Git commit `c3613fa9b0` — 上述逻辑调整
